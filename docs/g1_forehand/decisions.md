# Decision log

[繁體中文](decisions.zh-TW.md) · [Docs index](README.md)

| # | Decision | Why |
|---|---|---|
| D1 | Build on HOPE/HITTER rather than the hand-crafted `pingpong` prototype. | HITTER is proven on the G1; HOPE gives a complete, tested training/eval/deploy stack. |
| D2 | Start from Oren's `g1-port`. | It already solved the G1 asset, racket mount, joint-order pinning, MuJoCo plant parity and recipe scaling. |
| D3 | Robot = Unitree G1, simulation first, keep sim-to-real in mind. | The robot has not arrived. |
| D4 | A backhand side-backspin **serve** was planned and **shelved**. | Forehand rally is easier and higher priority. Plan kept in [`plans/serve_side_backspin.md`](plans/serve_side_backspin.md). |
| D5 | Train **forehand only**. | One swing is a smaller learning problem; backhand comes later. |
| D6 | Define success by the club's rally rule ([club rules](overview.md)), not HOPE's `success_rate`. | HOPE's analytic `success_rate` never clears the net (0 % even for the published A3 policy). |
| D7 | **Diagonal rally**: the feed is hit from the **opponent's right** to the robot's right; the robot returns from its right to the **opponent's** right. Four landing zones: one open-court and three lined up along the far end line. The feed bounce zone is fixed for now. | Club spec ([club rules](overview.md)). Feeding along the same diagonal matches a real cross-court rally. |
| D8 | Replace every training question with a G1-specific **apex-strike, cross-court bank**. | The inherited A3 bank strikes falling balls (median incoming vz −0.77 m/s), aims across the full table width, uses A3 reach (0.58 m, z 0.85–1.30 m), and covers only 25 % of questions. |
| D9 | Make reference motions from **human video** (GVHMR + GMR), as HITTER did. | `g1-port` clips are joint-space copies of the A3 swing; at its strike frame the racket is at ~0.78 m (table height), and the first G1 run was reach-limited (−9 cm x, −10 cm z). |
| D10 | Do not calibrate metrics against the A3 `model_21800`. | It does not work in our setup; metrics are verified with unit tests on known-good/bad racket states instead. |
| D11 | Run Isaac on SDSC from a **pip** install instead of the 64 GB container. | Podman cannot run on the BeeGFS home; the pip route needs no sudo. Node workarounds are scripted ([running it](operations/running.md)). |
| D12 | A lean HITTER-style reward (upper-body imitation + racket goal + base position + regularization) will be A/B-tested against the 53-term HOPE recipe. | **Pending**: needs the video clip first. |
| D13 | **One policy for all landing zones; the zone is chosen by the planner.** Positions are selectable modes (one or several) at run time, not separate policies. | The policy tracks a racket target; the planner/bank turns the chosen landing point into that racket velocity. One policy shares the body skill across zones, costs a quarter of the GPU time, and switches zones between shots without changing controllers. Per-zone evaluation (`target_zone_id`) shows whether a zone needs more weight or fine-tuning. |
| D14 | **Train at real rally timing, in a separate run (`g1_fh_rally`, task `HOPEPingPongUnitreeG1_FH_XC_RALLY`), warm-started from `g1_fh_diag`.** Up to 60 % of follow-up swings enter the clip late (time-to-strike 0.4–0.83 s, no hold) and the previous follow-through ends 0.7–1.0 s after its strike; the virtual ball arrives ±30 ms off the clock; feeds are faster (4.4–8.5 m/s before the bounce, was 4.4–6.6). All ramped in over 3000 iterations. | MuJoCo at real cadence (`--rally-pace`) dropped contact from 88 % to 38 % with falls on 44 % of balls: training gave 0.83 s of lead and ~3 s between strikes, a rally gives 0.4–0.8 s and ~1.5 s. Late entry is what the deploy reference clock does when the planner's time-to-strike is short, so no clip time-warp is needed. Slower feeds are impossible with the middle-third bounce and a fixed strike plane (the apex would be in front of the robot); they need forward footwork. The main run keeps going untouched as the comparison. |
| D15 | **A requeued run continues its step-keyed ramps; a warm start from another run restarts them.** `train.sbatch` passes `restore_step_counter=true` only when it resumes the run's own newest checkpoint. | Cluster outages and preemption requeue jobs. `runner.load` restores weights and optimizer but left `env.common_step_counter` at 0, so the rally-pace and timing-jitter ramps started over after every requeue. The counter is already saved in the checkpoint's exact-resume state. |
| D16 | **Treat the ball's spin as a required input, and do not buy cameras yet.** Plan a spin estimate from the opponent's racket at contact plus the ball's curved flight. | In simulation, perfect tracking without spin drops legal returns from 61 % to 10 %; with spin known, mocap and iPhone-level tracking score 56 % and 54 %, and a rough estimate (±50 %, ±40°) still gives 48–49 %. Camera quality matters far less than spin for our planner. Details: [`research/perception.md`](research/perception.md). |
| D17 | **Calibrate the deploy clock: the time-to-strike the policy sees must match training.** In MuJoCo a +60 ms offset is right; on hardware it will be measured again. | The racket reached the strike point 53 ms before its clock said so (20 ms from `lifecycle.py` subtracting a tick before the policy sees it, ~30 ms not yet explained), so every ball was hit ~45 ms before the apex. With +60 ms, apex OK goes 0 → 91 % and legal 57 → 78 % (`model_15400`). The 20 ms part is now fixed in code: `lifecycle.py` `clock: strike_time` (the G1 default since 2026-10-14; A3 keeps `countdown`) uses the planner's absolute deadline, with a guard against unsynced clocks; the rest is the calibration `lifecycle.tts_offset_s` (G1: 0.04 s from MuJoCo; re-measure on hardware). Status log 2026-10-14. |
| D18 | **Correct systematic aim errors in the planner (aim offset), not in the racket command; measure the offset with the real racket.** | Returns landed 30–60 cm short and drifted wide. Re-commanding the racket for its velocity bias made results worse (the policy does not follow out-of-distribution commands), while moving the planner's aim point by the mean miss tripled in-zone landings (11.7 → 35 % in MuJoCo, 34 % at rally pace). The offset depends on the racket contact (0.40 m vs 0.63 m for two racket models). Status log 2026-10-14. |
| D19 | **Train balance with random shoves** (new run `g1_fh_bal`: rally recipe + pushes ramped from 0 to ±0.5 m/s, ±0.4–0.6 rad/s every 3–6 s over 3000 iterations, warm start from the latest `g1_fh_diag`). It replaces resuming plain `g1_fh_rally`. | The HOPE/HITTER recipe has no pushes at all. MuJoCo push test: `g1_fh_diag` `model_15700` falls on 0 % of balls unpushed, 6 % at 0.5 m/s, 17 % at 0.75, 26 % at 1.0; `g1_fh_rally` `model_5900` already 10 % at 0.25 and 23 % at 0.5. A real robot gets bumped and steps on imperfect floors; 0.5 m/s is the size BeyondMimic trains its G1 with. |
| D20 | **Fist grip: the racket goes across the closed right fist, perpendicular to the forearm, red face on the palm side; retrain on it.** Separate model `unitree/URDF/g1_29dof_pingpang_fist/` (blade origin (0.083, 0.0226, 0.14) m, rpy (0, −90°, 0) in the wrist frame); new task `HOPEPingPongUnitreeG1_FH_FIST` (rally + shoves + fist mount + clips retargeted on the fist model). The old A3-style model stays for every existing run. *(Revised 2026-10-14: a first version only changed the hand's look and kept the racket along the forearm; that grip is impossible for a hand.)* | A fist holds a handle across the palm (see a shakehand grip), so the racket cannot point along the forearm. The current policies score 0 contacts with the fist model in MuJoCo, so retraining is required. The bank needs no change: IK puts the fist racket on 100 % of sampled bank strike points (< 3 cm, < 15°) with waist + arm. The two models are separate so the running `g1_fh_diag` is not affected on requeue. On the real G1 the rubber hand cannot close: we need a 3D-printed fist holder (or a dexterous hand) with the handle at this pose. |
| D21 | **Balance first: train a lower stance, the centre of mass over the feet and bigger shoves, weighted above the swing.** New task `HOPEPingPongUnitreeG1_FH_FIST_STABLE`: pelvis floor cost 0.70 → 0.58 m and a new ceiling cost above 0.66 m (`root_height_ceiling`, weight −1), a new cost when the whole-body CoM is more than 3 cm off the line between the feet (`com_support`, −2), shoves x/y 0.8 m/s, roll/pitch 0.6 rad/s, yaw 0.8 every 2–5 s, tilt cost (`upright` term: zero when standing straight, grows with the lean) −1 → −3, roll/pitch rate −0.05 → −0.15, post-swing tilt −0.7 → −1.5. Racket rewards unchanged. A second run `_FH_FIST_STABLE_SWING` adds the swing change on top (racket velocity std 0.6 → 0.4 m/s, position std 0.15 → 0.10 m) so its effect can be seen on its own. Both warm-start from `g1_fh_fist` `model_32299`. | On a real robot nothing works without balance (team decision, 2026-10-16). The pelvis stood at ~0.72 m in MuJoCo while the reference clip crouches at 0.675 m: an A3-derived floor cost (min 0.70 m) taxed every lower stance, so the robot was held up. Lower CoM = more margin against shoves. IK check: the fist racket reaches 100 % of bank strike points for any pelvis height 0.60–0.71 m. The remaining return error (~15 cm median) is scatter, which only a more precise swing can shrink. |
